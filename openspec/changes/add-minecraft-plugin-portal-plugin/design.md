# Design

Priority: nice to have, after the must-have changes.

## Context: descriptors

File names were checked against public documentation on 2026-11-14 where marked "docs"; the rest are stated from the platform's
long-standing convention and the implementation re-verifies each in its first test fixture.

| Platform | Descriptor in the jar | Format | Key fields | Source |
| --- | --- | --- | --- | --- |
| Bukkit, Spigot (also Folia flag, Nukkit) | `plugin.yml` | YAML | `name`, `version`, `main`, `description`, `author` or `authors`, `api-version`, `depend`, `softdepend`, `folia-supported` | convention |
| Paper | `paper-plugin.yml` | YAML | `name`, `version`, `main`, `description`, `api-version`, `authors`, `dependencies` with `bootstrap` and `server` sections, `bootstrapper`, `loader` | docs |
| BungeeCord, Waterfall | `bungee.yml` | YAML | `name`, `version`, `main`, `author`, `depends`, `softDepends`, `description` | convention |
| Velocity | `velocity-plugin.json` | JSON | `id`, `name`, `version`, `description`, `authors`, `dependencies`, `main`; generated by the `@Plugin` annotation processor or written by hand | docs (page confirms the file and its two origins; fields from the dedicated page, to verify) |
| Fabric | `fabric.mod.json` | JSON | `id`, `version`, `name`, `description`, `authors`, `depends`, `environment`, `icon` | convention |
| Quilt | `quilt.mod.json` | JSON | `quilt_loader` with `id`, `version`, `metadata` (`name`, `description`, `contributors`, `icon`), `depends` | convention |
| Forge | `META-INF/mods.toml` | TOML | `modLoader`, `loaderVersion`, `license`, `[[mods]]` with `modId`, `version`, `displayName`, `authors`, `description`, `[[dependencies.<modid>]]` | convention |
| NeoForge | `META-INF/neoforge.mods.toml` | TOML | same keys; `[[mods]]` with `modId`, `version`, `displayName`, `authors`, `description`, dependencies as `[[dependencies.<modid>]]` | docs (page documents only this file name) |
| Sponge (API 8 and later) | `META-INF/sponge_plugins.json` | JSON | `loader`, `license`, `plugins` array with `id`, `name`, `version`, `description`, `dependencies` | convention |
| Legacy Forge | `mcmod.info` | JSON | older mods only | convention, out of scope by default (Q6) |
| Minestom | none standard in the library itself; older extension loaders read `extension.json` | JSON | `name`, `entrypoint`, `version`, `dependencies` | unverified, Q5 |

A jar can hold several descriptors (a multi-loader mod holds `fabric.mod.json` and `META-INF/neoforge.mods.toml`). The plugin
records every loader it finds. Precedence for the display name and description: the first of (`paper-plugin.yml`, `plugin.yml`,
`fabric.mod.json`, `quilt.mod.json`, `META-INF/neoforge.mods.toml`, `META-INF/mods.toml`, `velocity-plugin.json`, `bungee.yml`,
`META-INF/sponge_plugins.json`) that parses.

Game versions are not uniform. Bukkit and Paper give `api-version` (a Minecraft minor, like `1.21`). Fabric and Forge express them
as dependency ranges on `minecraft` (`depends: { "minecraft": "~1.21" }`, `versionRange` in TOML). The plugin stores the declared
range text and, where it can reduce a range to concrete minors without guessing, a normalised list; anything else is stored as
text only and is not facetable (Q3).

## Findings in this repository

Paths are relative to `reposilite-backend/src/main/kotlin/` unless stated. The shared findings (events, `MavenFacade`, rights,
UI blocks, distribution of the API) are the same as in `add-gradle-plugin-portal-plugin/design.md`; only what is specific is here.

- **No hook with content.** `DeployEvent` carries repository, path and uploader only
  (`com/reposilite/maven/api/DeploymentApi.kt:35`). To read a jar the plugin must call `MavenFacade.findData`
  (`com/reposilite/maven/MavenFacade.kt:102`) again. That is workable for deploys, but there is no event for a reindex, a rebuild
  page (`net/onelitefeather/ingot/search/rebuild/RebuildService.kt:220-227`) or a proxied file, so existing artifacts and mirrors
  can only be found by a plugin-owned scan.
- **Index document is a file row.** `IndexRow` holds file record, provenance, size, modified, sha1, sha256, indexed at
  (`net/onelitefeather/ingot/search/IndexModel.kt:33`). The search SPI (`extract-search-backend-spi/design.md`, D1; public through
  `add-search-backend-registration/design.md`, D1) has `apply(actions)`, `pathsAt`, `existing`, `touch`, `deleteStale`,
  `deleteRepository`, `sample`; each takes file rows.
- **What the SPI lacks for this plugin** (all are statements about the current surface):
  1. no attributes on a row, so no `name`, `loader`, `mcVersions`, `authors`, `description`, `dependencies`;
  2. no multi-valued field and therefore no facet that counts "files per loader" over values (`facets` returns fixed buckets,
     `ArtifactSearchEngine.kt`, "The file counts per facet bucket");
  3. no filter by attribute in `ArtifactSearchQuery`; its filters are fixed fields, and free text `q` is tokenised over the GAV;
  4. no full text over a description; a backend such as OpenSearch could do it, the database backend would need a bounded
     `LIKE` over a lower-cased column;
  5. no document per project; the unit is a file, so one mod with ten versions is ten rows, and the portal has to group;
  6. no sort by attribute;
  7. no way for a backend to declare which attributes it can facet (`SearchBackendContext` has `environment`, `secret`, `logger`,
     `clock` only), so a plugin cannot adapt to a backend that does not support them;
  8. `SearchAccess` filtering is applied by the backend and repeated in the core (`add-search-backend-registration/design.md`,
     D6); attributes must go through the same path so a facet count never includes a row the viewer cannot read.
  The gaps are carried by `add-search-document-attributes` (1, 5, 7) and `add-search-attribute-facets` (2, 3, 4, 6, 8).
- **Viewer rights** are as in the Gradle proposal: `MavenFacade.canAccessResource` and `findRepositories`
  (`MavenFacade.kt:282,285`) plus `SearchAccessCompiler` (`net/onelitefeather/ingot/search/access/SearchAccessCompiler.kt:60`).
- **UI.** No card grid, no filter bar with facet counts, no icon or image block; `add-plugin-ui-extension-point` deliberately has no
  image block ("the model has no link or image block, so no address from a plugin is ever opened or loaded by the browser").
  A download link needs a `link` block restricted to the plugin's own routes or to Maven paths of the same host.
- **Existing parsers on the classpath.** `reposilite-backend` already ships Jackson (JSON, YAML module to be verified) and a
  `Groovy` plugin; no TOML parser is verified. The plugin brings its own parsers, shaded, versions pinned.

## Goals and non-goals

Goals: a browsable catalogue derived from jars; safe parsing; rights-aware listing; a visible list of core gaps.

Non-goals:

- No upload form, no moderation, no projects separate from Maven coordinates, no reviews, no download counts, no accounts.
- No dependency resolution for installing, no update checker, no launcher integration.
- No Modrinth or CurseForge API compatibility (maybe later, Q7).
- No execution of any jar code, ever. Descriptors are data.
- No change to Maven behaviour.

## Decisions

### D1: own repository, published API artifact only

Same as the Gradle proposal: `compileOnly` on the published API artifact, a clean-checkout CI build, a smoke test against the
current Ingot image. That job is the validation.

### D2: extraction runs from the enrichment hook, not from the deploy path

The extractor is an enricher (`add-artifact-enrichment-hook`) that runs in the index pipeline, off the request thread, for files with
extension `jar`. Deploy latency is unchanged and a failure cannot reach the deploying client. A deploy that stores a jar writes an
outbox entry already; the enricher runs when the worker applies it, and again on rebuild, which covers existing artifacts. Fallback
when the hook is declined: `DeployEvent` plus `MavenFacade.findData` on an executor owned by the plugin, and a scan on
`ReposiliteStartedEvent`; this misses proxied and replica-local cases and is not the plan.

### D3: stored attributes

Per jar file: `mc.loader` (multi: `bukkit`, `spigot`, `paper`, `folia`, `bungee`, `velocity`, `fabric`, `quilt`, `forge`,
`neoforge`, `sponge`, `minestom`), `mc.id`, `mc.name`, `mc.version`, `mc.description` (bounded to 2000 characters), `mc.authors`
(multi, each bounded), `mc.gameVersions` (multi, normalised minors), `mc.gameVersionRange` (text), `mc.dependencies` (multi,
`id` plus `required|optional`), `mc.icon` (path inside the jar, not the bytes), `mc.main`. Values are plain strings, length bounded
and control characters stripped. Nothing extracted is ever rendered as markup.

### D4: grouping and the portal model

A project is the Maven group and artifact. Cards show the latest version that matches the filters, its name and description, loaders
and game versions as chips, authors. The detail page shows all readable versions with date, size, loaders, game versions,
dependencies and the download path (`<repository>/<group path>/<artifact>/<version>/<artifact>-<version>.jar`, the plain Maven
URL, so Maven rights and statistics apply). Classifier jars (`-sources`, `-javadoc`) are not listed as downloads.

### D5: rights

As in the Gradle proposal D4. In addition: facet counts and totals are computed after the access filter, and the page never shows a
count that includes an unreadable row. A detail URL for an unreadable or unknown artifact answers `404`.

### D6: security of parsing

The jar is an untrusted, possibly hostile file uploaded by anyone with deploy rights, or fetched from a proxied upstream.

- **Zip limits.** The jar is opened through its central directory only; the plugin reads at most the named descriptors and the
  icon. Limits (defaults, configurable, with hard upper bounds in code): file size 256 MiB (larger is skipped), at most 20000
  entries, one descriptor at most 1 MiB uncompressed, compression ratio of a read entry at most 100:1, total bytes inflated per jar at
  most 4 MiB. Entry names with `..`, a leading `/` or a drive letter are ignored (they are never written to disk anyway; nothing is
  extracted to a file). Duplicate entry names: the first wins and a warning is logged.
- **Streaming and memory.** Entries are read through a counting stream that aborts at the limit; no entry is buffered whole above its
  limit. A bounded executor with a small thread count and a queue limit takes the work; a full queue skips the file (it is retried by
  the next rebuild) and does not block the pipeline.
- **Timeouts.** A per-jar deadline (default 5 seconds of wall time, measured with the injected clock in tests) aborts the work.
  A hung read on a remote storage backend is cut by closing the stream.
- **YAML.** SnakeYAML with `SafeConstructor` (or the Jackson YAML mapper with default typing off), `LoaderOptions` with
  `allowDuplicateKeys=false`, `maxAliasesForCollections` 50, `codePointLimit` set to the descriptor limit, `nestingDepthLimit` 50,
  and no global tags: no `!!` type construction. Only plain maps, lists, strings and numbers are accepted; everything else is a
  parse failure.
- **JSON.** A streaming parser with a depth limit, a string length limit, a total node limit and no polymorphic typing.
- **TOML.** A parser without include features, with the same size and depth limits.
- **Output.** Every extracted value is truncated to its bound and stripped of control characters, bidirectional override characters
  and line breaks (except in the description, where line breaks become spaces) before it is stored or shown.
- **Failure.** Any exception, limit, timeout or malformed descriptor is caught at the hook boundary: a warning with repository and
  path, a counter, no attributes for that file, and the pipeline continues. The deploy has already succeeded and cannot be affected.
  The enricher never throws into the core, and the hook isolates it anyway.
- **No code execution.** No class of the jar is loaded, no `Class.forName`, no annotation processing, no scripting of descriptor
  content. The jar is never opened with a `URLClassLoader`.
- **Bidirectional and homoglyph names.** A name that differs from the Maven coordinates is shown as the descriptor says, and the
  card also shows the coordinates, so a spoofed display name cannot hide the real artifact.

### D7: UI

A reader page `minecraft-portal` (`add-plugin-reader-pages`) with the list or card block, a filter bar with facet counts for loader
and game version, free text, and a detail page (`add-plugin-ui-browse-blocks`). No plugin script in the browser. Icons are optional
(D9).

### D8: configuration

Variables use the `INGOT_` prefix with the `REPOSILITE_` fallback and are read by the plugin through the context the API provides:
`INGOT_MCPORTAL_MAX_JAR_BYTES`, `INGOT_MCPORTAL_MAX_ENTRIES`, `INGOT_MCPORTAL_MAX_DESCRIPTOR_BYTES`,
`INGOT_MCPORTAL_TIMEOUT_MILLIS`, `INGOT_MCPORTAL_REPOSITORIES` (comma list; default empty means every repository the viewer
can read). Names are open (Q2).

### D9: icons (optional)

An icon is a PNG or SVG inside the jar. Serving it needs a route that reads the jar again, re-validates the content type by magic
bytes, refuses SVG with scripts (or serves SVG only as an image with `Content-Security-Policy: sandbox` and `nosniff`), caps size
and sets immutable cache headers keyed by digest. Default: no icons in the first version, a generated letter badge instead;
`add-plugin-asset-routes` is listed so the gap is visible.

## Alternatives considered

- **Read the POM only.** Rejected as the sole source: a POM lacks loader and game versions. Used for the description when the jar
  has none (never required).
- **Parse on request.** Rejected: cost and attack surface per page view.
- **A separate database owned by the plugin.** Rejected: second system of record, no cluster story, and the core has no stable
  persistence API for plugins (G8 of the Gradle design). The index is derived data and can be rebuilt.
- **Server side rendering to HTML by the plugin.** Rejected by `add-plugin-ui-extension-point` (data, not code).
- **Modrinth-compatible API.** Deferred (Q7).

## Risks

- **Descriptor drift.** Platforms change formats. Mitigation: one small parser per format with fixtures from real jars, and an
  unknown field is ignored.
- **Index load.** Reading jars at index time adds I/O. Mitigation: the bounds above, extension filter, and `touch` for unchanged
  files so a rebuild does not reread them (needs `add-artifact-enrichment-hook` to pass the checksum so the enricher can skip).
- **Backend support.** A search backend that cannot store attributes leaves the portal empty. Mitigation: the plugin checks the
  declared capabilities (G3) and shows a clear message.

## Open questions (each has a default)

- **Q1. Repository name.** Default `ingot-plugin-minecraft-portal`.
- **Q2. Variable names.** Default the `INGOT_MCPORTAL_` family in D8.
- **Q3. Game version normalisation.** Default: store the declared text always, normalise only simple forms (`1.21`, `~1.21`,
  `>=1.20 <1.22`), mark the rest unfacetable.
- **Q4. Which repositories are scanned.** Default every readable repository; operators can restrict with
  `INGOT_MCPORTAL_REPOSITORIES`.
- **Q5. Minestom.** Default: out of the first version. There is no stable descriptor to verify; add when the maintainers name the
  convention they use.
- **Q6. Legacy `mcmod.info`.** Default: out of scope.
- **Q7. Modrinth-style read API.** Default: not now.
- **Q8. Icons.** Default: none in the first version (D9).
- **Q9. Prerequisite order.** Default G1, G2, G3, G7 (shared) first; G4, G5, G6 next; G8 and G9 last.
