# Spec Delta

## Purpose

A release of Ingot names what is inside its standalone jar in a machine-readable form. The server jar and the dashboard each have a CycloneDX 1.6 SBOM, attached to the release next to the jar and attested to it, and the SBOMs are validated before a release and on every pull request. Nightlies, images and runtime behaviour do not change.

## ADDED Requirements

### Requirement: The server jar has a CycloneDX SBOM

The release SHALL attach a CycloneDX 1.6 JSON SBOM named `ingot-<version>.cdx.json` that lists the runtime classpath of the backend, generated by the build and not written by hand.

#### Scenario: Release with an SBOM

- **WHEN** a release is created
- **THEN** the release page carries `ingot-<version>.cdx.json` next to `ingot-<version>.jar`, and the file declares `bomFormat` `CycloneDX` and `specVersion` `1.6`

### Requirement: The dashboard has its own SBOM

The release SHALL attach a CycloneDX 1.6 JSON SBOM named `ingot-frontend-<version>.cdx.json` that lists the production npm packages of the dashboard from its lockfile.

#### Scenario: Dashboard packages

- **WHEN** a release is created
- **THEN** the dashboard SBOM contains every production package of `reposilite-frontend/package-lock.json` and none of the packages that are only needed for development

### Requirement: SBOMs are attested to the jar

The release workflow SHALL create an attestation for each SBOM whose subject is the standalone jar, and SHALL verify the attestations before the SBOMs are uploaded.

#### Scenario: Attestation verified

- **WHEN** the release has been published
- **THEN** `gh attestation verify` with the CycloneDX predicate type succeeds for the jar and for each SBOM

#### Scenario: Attestation fails

- **WHEN** an attestation step fails
- **THEN** neither SBOM is uploaded to the release

### Requirement: Invalid SBOMs never reach a release

The SBOMs SHALL be validated against the CycloneDX 1.6 schema and the required fields before they are attested. The same validation SHALL run on every pull request into `main`.

#### Scenario: Missing purl

- **WHEN** a component of an SBOM has no `purl`
- **THEN** the validation fails and the pull request check or the release job fails

#### Scenario: Dangling dependency reference

- **WHEN** a `dependencies` entry names a `bom-ref` that no component defines
- **THEN** the validation fails and names the reference

### Requirement: Nightlies carry no SBOM

The SBOM generation, validation and attestation steps MUST run only in the `jar` job, which runs only when a release was created. A nightly image and its push MUST NOT change.

#### Scenario: Push to main without a release

- **WHEN** a push to main creates no release
- **THEN** no SBOM is generated for release assets, no SBOM attestation is created, and the nightly image is handled as before

### Requirement: Permissions stay minimal

The `sbom` job that runs on pull requests SHALL declare `contents: read` only. The attestation permissions SHALL remain on the `jar` job alone.

#### Scenario: Pull request

- **WHEN** a pull request into `main` runs the `sbom` job
- **THEN** the job holds no write permission and no identity token request

### Requirement: Operators find the verification steps in the documentation

A how-to page under `docs/gitbook/how-to/` SHALL explain how to download the SBOMs, verify their attestations and read them, and `.github/RELEASE.md` SHALL list the release assets.

#### Scenario: Reading the how-to page

- **WHEN** an operator opens the page for verifying release SBOMs
- **THEN** the page contains the `gh attestation verify` command with the CycloneDX predicate type and the file names of the release assets
